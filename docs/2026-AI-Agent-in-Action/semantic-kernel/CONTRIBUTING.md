# Semantic Kernel에 기여하기

이슈와 풀 리퀘스트(PR)를 통해 Semantic Kernel에 기여할 수 있습니다. 발견한
문제에 대해 이슈를 등록하는 것만으로도 훌륭한 기여입니다. 코드 기여는
더욱 감사히 받고 있습니다.

## 이슈 보고하기

버그 리포트, API 제안 및 전반적인 피드백을 언제나 환영합니다. 이슈를 효과적으로
보고하기 위한 몇 가지 팁을 안내합니다.

### 보고 위치

새로운 이슈는 [이슈 목록](https://github.com/microsoft/semantic-kernel/issues)에서 등록할 수 있습니다.

새 이슈를 등록하기 전에, 동일한 이슈가 이미 존재하지 않는지 이슈 목록을
검색해 주세요.

보고하려는 내용에 대한 기존 이슈를 발견한 경우, 토론에 직접 피드백을
추가해 주세요. 원본 게시물에 추천(👍 반응)을 눌러 주시면, 백로그에서 인기 있는
이슈의 우선순위를 정하는 데 도움이 됩니다.

### 좋은 버그 리포트 작성하기

좋은 버그 리포트는 메인테이너가 근본 원인을 파악하고 검증하는 것을
더 쉽게 만듭니다.
버그 리포트가 상세할수록 문제가 더 빠르게 해결됩니다. 이상적으로 버그
리포트에는 다음 정보가 포함되어야 합니다:

- 문제에 대한 개괄적인 설명.
- _최소 재현 사례_, 즉 잘못된 동작을 재현하는 데 필요한 최소한의 코드/설정.
- _예상 동작_과 관찰된 _실제 동작_에 대한 비교 설명.
- 환경 정보: OS/배포판, CPU 아키텍처, SDK 버전 등.
- 추가 정보, 예: 이전 버전 대비 리그레션인지? 알려진 해결 방법이 있는지?

## 변경 사항 기여하기

프로젝트 메인테이너가 기여자의 승인된 코드 변경 사항을 병합합니다.

### 해야 할 것과 하지 말아야 할 것

해야 할 것:

- **DO** 표준 코딩 규칙을 따르세요

  - [.NET](https://learn.microsoft.com/dotnet/csharp/fundamentals/coding-style/coding-conventions)
  - [Python](https://pypi.org/project/black/)
  - [Typescript](https://typescript-eslint.io/rules/)/[React](https://github.com/jsx-eslint/eslint-plugin-react/tree/master/docs/rules)

- **DO** 변경하는 프로젝트나 파일의 기존 스타일이 일반 가이드라인과 다를 경우, 기존 스타일을 우선하세요.
- **DO** 새로운 기능을 추가할 때 테스트를 포함하세요. 버그를 수정할 때는 현재 동작이 어떻게 잘못되었는지 보여주는 테스트를 먼저 추가하세요.
- **DO** 토론의 초점을 유지하세요. 새로운 주제나 관련 주제가 나오면 토론을 벗어나기보다 새 이슈를 생성하는 것이 좋습니다.
- **DO** 이슈에 대해 구현을 담당하겠다고 명확히 밝혀 주세요.
- **DO** 기여에 대해 블로그, 트윗(또는 다른 방법으로) 자주 공유하세요!

하지 말아야 할 것:

- **DON'T** 큰 풀 리퀘스트로 깜짝 놀라게 하지 마세요. 대신, 이슈를 등록하고 토론을 시작하여 많은 시간을 투자하기 전에 방향에 대해 합의하세요.
- **DON'T** 직접 작성하지 않은 코드를 커밋하지 마세요. Semantic Kernel에 적합하다고 생각되는 코드를 발견하면, 진행하기 전에 이슈를 등록하고 토론을 시작하세요.
- **DON'T** 라이선스 관련 파일이나 헤더를 변경하는 PR을 제출하지 마세요. 문제가 있다고 생각되면 이슈를 등록해 주시면 기꺼이 논의하겠습니다.
- **DON'T** 이슈를 등록하고 먼저 논의하지 않고 새로운 API를 만들지 마세요.

### 호환성을 깨는 변경 사항

기여는 API 시그니처와 동작 호환성을 유지해야 합니다. 호환성을 깨는 변경 사항이
포함된 기여는 거부됩니다. 호환성을 깨는 변경이 필요하다고 판단되면
이슈를 등록하여 아이디어나 변경 사항을 논의해 주세요.

### 권장 워크플로

다음 워크플로를 사용하고 권장합니다:

1. 작업에 대한 이슈를 생성합니다.
   - 사소한 변경의 경우 이 단계를 생략할 수 있습니다.
   - 해당 주제에 대한 기존 이슈가 있으면 재사용하세요.
   - 제안한 변경 사항이 적절한지 팀과 커뮤니티의 동의를 얻으세요.
   - 구현을 담당할 경우 명확히 밝혀 주세요. 이슈가 본인에게 할당되도록
     요청할 수 있습니다. 참고: 이슈 등록자와 구현자가 동일인일 필요는 없습니다.
2. GitHub에서 리포지토리의 개인 포크를 생성합니다(아직 없는 경우).
3. 포크에서 main으로부터 브랜치를 생성합니다(`git checkout -b mybranch`).
   - 의도를 명확히 전달할 수 있도록 브랜치 이름을 지정하세요.
     예: "issue-123" 또는 "githubhandle-issue".
4. 브랜치에 변경 사항을 커밋합니다.
5. 해당되는 경우 변경 사항에 대한 새로운 테스트를 추가합니다.
6. [아래 섹션](https://github.com/microsoft/semantic-kernel/blob/main/CONTRIBUTING.md#dev-scripts)의 관련 스크립트를 실행하여 빌드가 깨끗하고 모든 테스트가 통과하는지 확인합니다.
7. 리포지토리의 **main** 브랜치에 대한 PR을 생성합니다.
   - 설명에 PR이 해결하는 이슈 또는 개선 사항을 명시합니다.
   - 모든 지속적 통합(CI) 체크가 통과하는지 확인합니다.
8. 코드 메인테이너의 피드백이나 변경 사항 승인을 기다립니다.
9. 담당자가 승인하고 모든 체크가 통과하면 PR이 병합됩니다.

### 개발 스크립트

아래 스크립트는 프로젝트 내에서 빌드, 테스트 및 린트를 수행하는 데 사용됩니다.

- Python: [python/DEV_SETUP.md](https://github.com/microsoft/semantic-kernel/blob/main/python/DEV_SETUP.md#pipeline-checks)를 참조하세요.
- .NET:
  - 빌드/테스트: `run build.cmd` 또는 `bash build.sh`
  - 린트(자동 수정): `dotnet format`
- Typescript:
  - 빌드/테스트: `yarn build`
  - 린트(자동 수정): `yarn lint:fix`

### 플러그인 및 메모리 커넥터 추가

Semantic Kernel에 대한 플러그인 및 메모리 커넥터 기여를 고려할 때
다음 가이드라인을 참고해 주세요:

#### 플러그인

플러그인을 통해 Semantic Kernel의 기능을 확장하는 데 관심을 가져 주셔서
감사합니다. 다만, GitHub 리포지토리 내 플러그인 호스팅에 대한 접근 방식을
안내드립니다. 깨끗하고 관리 가능한 코드베이스를 유지하기 위해 Semantic Kernel
GitHub 리포지토리에 직접 플러그인을 호스팅하지 않습니다.
대신, 기여자가 자신의 GitHub 계정이나 조직 하의 별도 리포지토리에 플러그인
코드를 호스팅하시길 권장합니다. 그런 다음 Semantic Kernel 리포지토리의 관련
토론, 이슈 또는 문서에서 플러그인 리포지토리 링크를 제공할 수 있습니다.
이 접근 방식은 각 플러그인을 독립적으로 유지 관리할 수 있게 하며, 각 플러그인에
특화된 업데이트 및 이슈를 더 쉽게 추적할 수 있게 합니다.

#### 메모리 커넥터

메모리 커넥터의 경우, Semantic Kernel 리포지토리 내에서 직접 호스팅을 추가하지
않지만, 메모리 커넥터를 별도의 플러그인으로 빌드하시길 강력히 권장합니다.
메모리 커넥터는 외부 메모리 시스템과의 인터페이스에서 중요한 역할을 하며,
플러그인으로 취급하면 모듈성과 유지보수성이 향상됩니다.

### PR - CI 프로세스

지속적 통합(CI) 시스템이 PR에 대해 필요한 빌드를 자동으로 수행하고
테스트(여러분이 실행해야 하는 테스트 포함)를 실행합니다. 빌드와 테스트
실행은 깨끗해야 합니다.

어떤 이유로든 CI 빌드가 실패하면, 실패 원인을 파악하는 데 사용할 수 있는
링크와 함께 PR 이슈가 업데이트됩니다.
