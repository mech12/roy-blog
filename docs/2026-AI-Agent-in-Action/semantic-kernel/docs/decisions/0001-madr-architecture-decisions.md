# Semantic Kernel 아키텍처 결정을 추적하기 위해 Markdown Any Decision Records 사용

## 배경 및 문제 상황

C#, Python, Java, Typescript 등 여러 언어 버전의 Semantic Kernel이 활발하게 개발되고 있습니다.
주요 아키텍처 결정 사항에 대해 구현을 일관되게 유지할 방법이 필요합니다. 예를 들어, 시맨틱 함수 구성(`config.json`)에 사용되는 형식 변경을 검토 중이며, 이 변경이 합의되면 모든 Semantic Kernel 구현에 반영되어야 합니다.

MADR은 구조화된 방식으로 모든 결정을 기록하기 위한 간결한 템플릿입니다. 이 템플릿은 원래 아키텍처 결정을 기록하기 위해 만들어졌으며, 이후 모든 종류의 결정을 기록할 수 있는 템플릿으로 발전했습니다.
자세한 정보는 [여기](https://adr.github.io/)를 참조하세요.

## 결정 동인

- 아키텍처 변경과 관련된 의사결정 과정은 커뮤니티에 투명하게 공개되어야 합니다.
- 결정 기록은 저장소에 저장되며, 다양한 언어 포팅에 참여하는 팀들이 쉽게 찾을 수 있어야 합니다.

## 검토된 옵션

- MADR 형식을 사용하고 결정 문서를 저장소에 저장합니다.

### MADR 형식을 사용하고 결정 문서를 저장소에 저장

기술 결정을 추적하기 위해 ADR을 어떻게 사용할 것인가?

1. docs/decisions/adr-template.md를 docs/decisions/NNNN-title-with-dashes.md로 복사합니다. NNNN은 순서상 다음 번호를 나타냅니다.
   1. 올바른 순서 번호를 사용하기 위해 기존 PR을 확인하세요.
   2. 간략 양식 템플릿 docs/decisions/adr-short-template.md도 있습니다.
2. NNNN-title-with-dashes.md를 편집합니다.
   1. 상태는 처음에 `proposed`여야 합니다.
   2. `deciders` 목록에는 결정에 서명할 사람들의 별칭이 포함되어야 합니다.
   3. 관련 EM과 `dluc`가 모든 결정의 deciders 또는 informed에 포함되어야 합니다.
   4. 결정 과정에서 협의한 모든 파트너의 별칭을 나열해야 합니다.
3. 각 옵션에 대해 검토된 각 대안의 좋은 점, 중립적인 점, 나쁜 점을 나열합니다.
   1. 상세 조사 내용은 `추가 정보` 섹션에 인라인으로 포함하거나 외부 문서 링크로 포함할 수 있습니다.
4. PR을 deciders 및 기타 관심 있는 당사자들과 공유합니다.
   1. Deciders는 필수 리뷰어로 지정되어야 합니다.
   2. 결정이 합의되면 상태를 `accepted`로 업데이트하고 날짜도 업데이트해야 합니다.
   3. 결정 승인은 PR 승인을 통해 기록됩니다.
5. 결정은 나중에 변경될 수 있으며 새로운 ADR로 대체될 수 있습니다. 이 경우 원래 ADR에 부정적인 결과를 기록하는 것이 유용합니다.
