# 오류 처리 개선

## 면책 조항

이 ADR은 SK의 오류 처리 측면을 개선하기 위한 문제점과 해결 방안을 설명합니다. 로깅, 복원력 또는 관측성 측면은 다루지 않습니다.

## 배경 및 문제 상황

현재 SK의 오류 처리에는 SK 코드와 SK 클라이언트 코드를 단순화하면서 일관성과 유지보수성을 보장하기 위해 개선할 수 있는 여러 측면이 있습니다:

- **예외 전파**. SK에는 Kernel.RunAsync와 SKFunction.InvokeAsync 같은 몇 가지 공개 메서드가 비표준 방식으로 예외를 처리합니다. 예외를 던지는 대신 SKContext에 잡아서 저장합니다. 이는 .NET의 표준 오류 처리 접근 방식과 다릅니다. .NET에서는 계약이 충족되면 메서드가 성공적으로 실행되거나, 계약이 위반되면 예외를 던지는 것이 기대됩니다. 따라서 .NET 버전의 SK SDK를 사용할 때 SKContext 인스턴스의 특정 속성을 분석하지 않고는 메서드가 성공적으로 실행되었는지 실패했는지 판단하기 어렵습니다. 이는 .NET SK SDK를 사용하는 개발자에게 좌절감을 줄 수 있습니다.

- **부적절한 예외 사용**. 일부 SK 구성 요소는 잘못된 인수, 구성 문제 등을 나타내기 위해 표준 .NET 예외 대신 사용자 정의 SK 예외를 사용합니다. 이는 .NET의 표준 오류 처리 접근 방식과 다르며 SK 클라이언트 코드 개발자에게 좌절감을 줄 수 있습니다.

- **예외 계층 구조**. 사용자 정의 SK 예외의 절반은 SKException에서 파생되고, 나머지 절반은 Exception에서 직접 파생됩니다. 이러한 예외 계층 구조의 불일치는 응집력 있는 예외 모델에 기여하지 않습니다.

- **불필요하고 장황한 예외**. Kernel이나 Planner 같은 일부 SK 구성 요소에는 PlanningException이나 KernelException 같은 해당 수준의 예외가 있으며, 이는 실제로 필요하지 않고 SKException과 몇 가지 파생 클래스로 쉽게 대체할 수 있습니다. SK 클라이언트가 이에 의존하게 되면 나중에 SK가 사용을 중단해야 할 때 제거하기 어려울 수 있습니다. 또한 SK에는 각 SK 메모리 커넥터마다 예외 타입이 있습니다(PineconeMemoryException, QdrantMemoryException). 이들은 추가 정보를 제공하지 않으며 동일한 멤버 시그니처를 가지면서 이름만 다릅니다. 이로 인해 SK 클라이언트 코드가 이를 통합적으로 처리하는 것이 불가능합니다. 단일 catch 블록 대신 각 구성 요소 구현마다 catch 블록이 필요합니다. 게다가 새로운 구성 요소 구현이 추가되거나 제거될 때마다 SK 클라이언트 코드를 업데이트해야 합니다.

- **원본 예외 세부 정보 누락**. 특정 SK 예외는 원래의 실패나 예외 세부 정보를 보존하지 않으며 속성을 통해 노출하지 않습니다. 이 누락은 SK 클라이언트 코드가 문제를 이해하고 적절하게 처리하는 것을 방해합니다.

## 결정 동인

- 예외는 SKContext에 저장되는 대신 SK 클라이언트 코드로 전파되어야 합니다. 이 조정으로 SK 오류 처리가 .NET 접근 방식에 부합하게 됩니다.
- SK 예외 계층 구조는 "적을수록 좋다"는 원칙에 따라 설계되어야 합니다. 나중에 새로운 예외를 추가하는 것은 쉽지만 제거하는 것은 어려울 수 있습니다.
- .NET 표준 예외 타입은 쉽게 인식할 수 있고, 유지보수가 필요 없으며, 일반적인 오류 시나리오를 다룰 수 있고, 의미 있고 표준화된 오류 메시지를 제공하므로 SK 사용자 정의 타입보다 선호되어야 합니다.
- 예외를 호출자에게 전달할 때 SK 또는 SK 클라이언트 코드에 대한 실행 가능한 로직 구성에 도움이 되지 않는 한 SK 예외로 래핑해서는 안 됩니다.

## 검토된 옵션

- SKException을 제외한 모든 사용자 정의 예외 타입과 실행 가능하지 않은 타입을 제거하여 기존 SK 예외 계층 구조를 단순화합니다. 더 많은 세부 정보를 전달해야 하는 경우가 아니면 제거된 타입 대신 SKException 타입을 사용하고, 필요한 경우 파생된 특정 예외를 생성합니다.
- 사용자 정의 SK 예외를 던지는 대신 클래스 인수 값이 제공되지 않거나 유효하지 않을 때 ArgumentOutOfRangeException이나 ArgumentNullException 같은 .NET 표준 예외를 던지도록 SK 코드를 수정합니다. SK 예외 사용을 분석하여 표준 .NET 예외를 대신 사용할 수 있는 다른 잠재적 영역을 식별하고 수정합니다.
- 단순히 래핑 목적으로 처리되지 않은 예외를 AIException이나 다른 SK 예외로 래핑하는 코드를 제거합니다. 대부분의 경우 이 코드는 일반적이고 유용하지 않은 "문제가 발생했습니다" 메시지 외에 실행 가능한 유용한 정보를 제공하지 않습니다.
- 원본 예외가 다시 던져진 SK 예외의 내부 예외로 보존되지 않는 모든 경우를 식별하고 해결합니다.
- StatusCode 속성을 포함하는 새로운 예외 HttpOperationException을 생성하고, HttpStatusCode, HttpRequestException 또는 Azure.RequestFailedException에서 예외를 매핑하는 데 필요한 로직을 구현합니다. HTTP 스택과 상호작용하는 기존 SK 코드를 업데이트하여 실패한 HTTP 요청의 경우 HttpOperationException을 던지고 원본 예외를 내부 예외로 할당합니다.
- 현재 예외를 SK 컨텍스트에 저장하는 모든 SK 구성 요소를 수정하여 대신 다시 던지도록 합니다.
- IsCriticalException 확장 메서드를 수정하여 StackOverflowException과 OutOfMemoryException 예외 처리를 제외함으로써 SK 치명적 예외 처리 기능을 단순화합니다. 전자의 예외는 던져지지 않으므로 호출 코드가 실행되지 않고, 후자의 예외는 반드시 복구 코드 실행을 방해하지는 않기 때문입니다.
