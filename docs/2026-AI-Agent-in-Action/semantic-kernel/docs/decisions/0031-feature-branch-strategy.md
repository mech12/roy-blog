# 커뮤니티 주도 커넥터 및 기능을 위한 전략

## 배경 및 문제 설명

일반적으로 커넥터는 한 사람 또는 팀이 개발할 수 있는 중간~복잡 수준의 새로운 기능입니다. 충돌을 방지하고 개발 프로세스를 더 잘 통제하기 위해, 우리 저장소에서 기능 브랜치 전략의 사용을 강력히 권장합니다.

현재 소프트웨어 개발 프로세스에서 main 브랜치의 변경 사항 관리가 점점 복잡해지면서, 잠재적인 충돌과 릴리스 주기 지연이 발생하고 있습니다.

## 표준 및 가이드라인 원칙

- **패턴**: 기능 브랜치 전략은 코드베이스의 변경 사항을 관리하기 위한 잘 알려진 패턴입니다. 업계에서 널리 사용되며 GitHub을 포함한 대부분의 버전 관리 시스템에서 지원됩니다. 이는 또한 커뮤니티가 SK의 커넥터나 기타 대규모 기능 개발에 어떻게 의미 있게 기여할 수 있는지에 대한 명확한 그림을 제공합니다.
- **격리된 개발 환경**: 기능 브랜치를 사용하면 각 개발자가 다른 사람의 작업을 방해하지 않고 프로젝트의 다른 측면에서 작업할 수 있습니다. 이 격리는 충돌을 줄이고 main 브랜치가 안정적으로 유지되도록 보장합니다.
- **간소화된 통합**: 기능 브랜치는 새 코드를 main 브랜치에 통합하는 프로세스를 단순화합니다. 더 작고 관리 가능한 변경 사항을 처리함으로써 통합 시 주요 충돌의 위험을 최소화합니다.
- **코드 리뷰의 효율성**: 기능 브랜치의 더 작고 집중된 변경 사항은 더 빠르고 효율적인 코드 리뷰를 이끕니다. 이 효율성은 한 번에 적은 코드를 리뷰하는 용이성뿐만 아니라 변경 사항의 맥락과 영향을 이해하는 데 절약되는 시간에 관한 것입니다.
- **버그 위험 감소**: 기능 브랜치에서 개발을 격리하면 main 브랜치에 버그가 도입될 가능성이 줄어듭니다. 단일 기능의 제한된 맥락 내에서 문제를 식별하고 수정하기가 더 쉽습니다.
- **적시 기능 통합**: 작고 점진적인 풀 리퀘스트는 더 빠른 리뷰와 기능 브랜치로의 빠른 기능 통합을 가능하게 하며, 코드가 이미 이전에 리뷰되었으므로 main으로의 병합을 더 쉽게 만듭니다. 이 적시성은 기능이 더 빨리 병합되고 배포 준비가 되도록 보장하여 변경에 대한 대응성을 향상시킵니다.
- **코드 테스트, 커버리지 및 품질**: 좋은 코드 품질을 유지하기 위해 코드베이스에 도입되는 모든 새 코드나 기능은 적절하게 테스트되고 검증되어야 합니다. 모든 새 기능이나 코드는 단위 테스트와 통합 테스트로 커버되어야 합니다. 코드는 또한 CI/CD 파이프라인에 의해 검증되고 코드 품질 표준 및 가이드라인을 따라야 합니다.
- **예제**: 모든 새 기능이나 코드에는 새 기능이나 코드의 사용 방법을 보여주는 예제가 함께 제공되어야 합니다. 이는 새 기능이나 코드가 적절히 문서화되고 커뮤니티가 쉽게 이해하고 사용할 수 있도록 보장하는 데 중요합니다.
- **서명**: 최종적으로 패키지가 될 커넥터는 `SK-dotnet.sln` 파일에서 패키지 및 어셈블리 서명이 활성화되어야 합니다(Publish = Publish로 설정).
  ```
  {Project GUID}.Publish|Any CPU.ActiveCfg = Publish|Any CPU
  {Project GUID}.Publish|Any CPU.Build.0 = Publish|Any CPU
  ```

### 커뮤니티 기능 브랜치 전략

기여자가 잠재적 커넥터 구현으로서 기능 이슈를 담당/생성하려는 의향이 있음을 식별하면, 해당 기능에 대한 새 브랜치를 생성합니다.

새 커넥터를 수용하기로 합의하면, 구현이 진행되고 필요한 경우 지원되도록 기여자와 협력합니다.

기여자(들)는 우리의 감독과 리뷰 프로세스 하에 기능 브랜치에 작은 풀 리퀘스트를 통해 점진적으로 대부분의 변경 사항을 추가할 책임 중 하나를 맡게 됩니다.

이 전략은 커넥터와 같은 각 새로운 대규모 기능에 대해 저장소에 별도의 브랜치를 생성하는 것을 포함합니다. 이 격리는 main 브랜치에 영향을 주지 않고 통제된 환경에서 변경이 이루어진다는 것을 의미합니다.

필요한 경우 기능 브랜치에 대한 개발과 변경에 참여할 수도 있으며, PR에 대한 변경 사항 및 전체 또는 공동 저자는 릴리스 노트에 적절히 추적되고 참조됩니다.

#### 장단점

- 좋음, 한 번에 하나의 기능에 집중한 개발을 가능하게 함.
- 좋음, 더 작고 점진적인 풀 리퀘스트(PR)를 촉진하여 리뷰 프로세스를 단순화함.
- 좋음, 주요 버그가 main 브랜치에 병합되는 위험을 줄임.
- 좋음, 기능을 main 브랜치에 통합하는 프로세스를 더 쉽고 빠르게 만듦.
- 나쁨, 적절히 관리되지 않으면 main 브랜치와 정기적으로 동기화되지 않아 오래된 브랜치가 될 수 있음.

## 로컬 배포 플랫폼 / 오프라인

### LM Studio

LM Studio는 모델을 로컬에 배포하는 데 사용할 수 있는 로컬 배포 옵션이 있습니다. 이 옵션은 Windows, Linux, MacOS에서 사용 가능합니다.

장점:

- API가 OpenAI API와 매우 유사
- 이미 많은 모델이 지원됨
- 사용하기 쉬움
- 배포하기 쉬움
- GPU 지원

단점:

- 업무 환경에서 사용하려면 라이선스가 필요할 수 있음

### Ollama

Ollama는 모델을 로컬에 배포하는 데 사용할 수 있는 로컬 배포 옵션이 있습니다. 이 옵션은 현재 Linux와 MacOS에서만 사용 가능합니다.

장점:

- 사용하기 쉬움
- 배포하기 쉬움
- Docker 배포 지원
- GPU 지원

단점:

- API가 OpenAI API와 유사하지 않음(전용 커넥터 필요)
- Windows 지원 없음

## 자주 묻는 질문

### 포크를 통한 기존 기여 방식을 따르던 이니셔티브에 대한 마이그레이션 전략이 있나요? 이제 microsoft/semantic-kernel의 브랜치로 전환해야 하는데요.

포크와 `main`을 대상으로 하는 PR을 통해 정상적으로 진행합니다. 귀하의 main에 대한 기여 PR이 크고 바람직한 기능(이 ADR에서 기대하는 것으로 설명한 것을 참조)임을 식별하면, 귀하의 포크 PR을 리타겟팅할 수 있는 전용 기능 브랜치(`feature-yourfeature`)를 생성합니다.
이후의 모든 점진적 변경 사항과 기여는 정상적으로 진행되지만, `main` 대신 `feature-*` 브랜치를 대상으로 합니다.

### "main 브랜치와 최신 상태 유지" 문제를 어떻게 해결할 건가요?

이것은 현재 기능 구현이 완료되고 `main`에 병합할 준비가 되었다고 모두 합의했을 때 발생합니다.

기능이 완료되면 main에서 기능 브랜치로 병합이 푸시됩니다.
이는 일반적으로 정리해야 할 충돌을 유발합니다.
이것은 보통 기능 브랜치를 대상으로 하는 마지막 PR이 되며, 바로 뒤에 충돌이 거의 없는 `feature` 브랜치에서 `main`을 대상으로 하는 또 다른 PR이 이어집니다.
main으로의 병합은 빠를 수 있습니다(모든 중간 기능 PR이 이전에 합의되고 승인되었으므로).

### 기능 완료 전에 main 브랜치를 기능 브랜치에 병합

main 브랜치를 기능 브랜치에 병합할 때는 다음 명령어만 사용해야 합니다:

`git checkout <feature branch> && git merge main` --squash 없이

main에서의 병합은 기능 브랜치로의 PR로 절대 수행하면 안 됩니다. 이는 main 병합 히스토리가 PR 히스토리와 합쳐지게 하고(PR은 --squash로 병합되므로), 결과적으로 이후 main 병합 시 이상한 충돌을 생성하며 기능 브랜치의 히스토리 분석을 어렵게 만듭니다.
