# Java 저장소를 별도의 코드베이스로 분리

## 컨텍스트 및 문제 설명

단일 저장소에서 여러 언어를 관리하면, 서로 다른 언어와 빌드 도구가 저장소를 관리하는 방식에 대해 몇 가지 과제가 발생합니다. 특히 Java의 일반적인 빌드 도구인 Apache Maven이 저장소와 상호작용하는 방식에서 그렇습니다. 일반적으로 Maven 릴리스를 수행할 때는 릴리스를 준비하는 동안 커밋이 추가되지 않도록 저장소를 동결해야 합니다. 공유 저장소에서 이를 달성하려면 이 과정 동안 모든 언어의 풀 리퀘스트 머지를 중단해 달라고 요청해야 합니다. Maven 릴리스 프로세스는 또한 프로젝트가 원하는 스쿼시 머지와도 잘 호환되지 않는데, 이는 일반적인 Maven 릴리스 프로세스가 저장소에 여러 커밋을 푸시해야 하기 때문입니다.

또한 발견 가능성 관점에서, 원래 저장소에서는 현재 풀 리퀘스트, 이슈 및 활동의 대부분이 다른 언어에서 발생합니다. 이로 인해 사용자들 사이에서 Semantic Kernel 저장소가 Java에 적합한 저장소인지에 대한 혼란이 있었습니다. diff 확인이나 릴리스 노트 작성과 같은 작업 시 git 히스토리를 관리하는 것도 대부분의 커밋과 코드가 Java와 무관하기 때문에 상당히 어렵습니다.

또한 모든 언어가 선호하는 저장소 정책을 관리하는 것도 과제입니다. 여러 언어를 빌드하는 것을 고려해야 하므로 더 복잡한 빌드 프로세스를 만들어야 합니다. 사용자가 자신의 언어 외부의 저장소에 실수로 변경을 가하거나 공통 파일에 변경을 가하면 다른 언어의 승인이 필요하게 되어, 다른 언어의 사용자 리뷰가 필요하게 되면서 지연이 발생합니다. 마찬가지로 GitHub Actions 워크플로우, `.gitignore`, VS Code 설정, `README.md`, `.editorconfig` 등의 공통 파일도 여러 언어를 동시에 지원해야 하므로 더 복잡해집니다.

커뮤니티 관점에서, 별도의 저장소를 갖는 것은 커뮤니티 참여를 촉진하여 개발자들이 Java 프로젝트에만 기여하고, 아이디어를 공유하고, 협업할 수 있게 합니다.
또한 기여를 투명하게 추적할 수 있어 주요 기여자를 식별하고 그들의 노력을 인정하기 쉽습니다.
단일 저장소를 갖는 것은 커밋, 풀 리퀘스트 및 기타 활동에 대한 유용한 통계를 제공하여, 유지 관리자가 프로젝트 진행 상황과 활동 수준을 모니터링하는 데 도움이 됩니다.

## 결정 요인

- Java 도구와 호환되는 프로젝트 설정 허용
- 커뮤니티가 Java 프로젝트를 발견하고 상호작용하는 능력 향상
- 커뮤니티가 Java 프로젝트의 변경 사항을 독립적으로 관찰할 수 있는 능력 향상
- 단일 언어에 집중하여 저장소 빌드/파일 단순화

## 고려된 옵션

과거에 [Semantic Kernel](https://github.co/microsoft/semantic-kernel) 저장소 내의 별도 브랜치에서 운영한 적이 있는데, 이는 일부 문제를 해결했지만 사용자들이 메인 브랜치에서 최신 코드를 찾을 것으로 기대하기 때문에 사용자 발견 가능성을 크게 저해했습니다.
