# Integration Test vs Regression Test vs E2E Test

세 가지는 **서로 다른 분류 축**에 속한다. "vs"로 비교하기 쉽지만, 사실 같은 선상에 놓을 수 없는 개념이다.

---

## 핵심: 분류 축이 다르다

```
 분류 축 ①  테스트 범위(Scope) — "얼마나 넓게 테스트하는가?"
 ──────────────────────────────────────────────────
   Unit  →  Integration  →  E2E
   함수       모듈 연동       전체 시스템

 분류 축 ②  테스트 목적(Purpose) — "왜 이 테스트를 돌리는가?"
 ──────────────────────────────────────────────────
   Smoke       — 최소한 뜨는지 확인
   Regression  — 변경 후 기존 기능이 안 깨졌는지 확인
   Acceptance  — 요구사항을 충족하는지 확인
```

Integration Test와 E2E Test는 **축 ①(범위)**, Regression Test는 **축 ②(목적)**에 속한다. 따라서 이 셋은 대등 비교가 아니라 **조합**해서 쓰는 관계이다.

> 예: "Integration Test를 Regression 목적으로 매 커밋마다 돌린다"

---

## Integration Test (통합 테스트)

**목적**: 모듈/서비스 간 **연동 지점**이 제대로 동작하는지 검증

```
┌──────────┐     ┌──────────┐     ┌──────────┐
│ Service A │ ──→ │ Service B │ ──→ │    DB    │
└──────────┘     └──────────┘     └──────────┘
       ↑                                ↑
       └── 이 연결이 정상인지 테스트 ────┘
```

| 항목 | 내용 |
|------|------|
| 테스트 대상 | API 호출, DB 쿼리, 메시지 큐, 외부 서비스 연동 |
| 실제 의존성 | 실제 DB/서비스를 사용하거나 테스트 컨테이너 활용 |
| 예시 | "주문 서비스가 결제 서비스 API를 호출하면 정상 응답을 받는가?" |
| 속도 | 중간 (네트워크/DB I/O 포함) |

```python
# 예: FastAPI + PostgreSQL 통합 테스트
def test_create_user_and_read_from_db():
    response = client.post("/users", json={"name": "Roy"})
    assert response.status_code == 201

    user = db.query(User).filter_by(name="Roy").first()
    assert user is not None  # DB에 실제로 저장되었는지 확인
```

## E2E Test (End-to-End 테스트)

**목적**: 실제 사용자 시나리오 전체를 **처음부터 끝까지** 검증

```
┌────────┐    ┌────────┐    ┌────────┐    ┌────────┐
│ Browser │ →  │ Frontend│ →  │ Backend │ →  │   DB   │
│ (User)  │    │        │    │        │    │        │
└────────┘    └────────┘    └────────┘    └────────┘
 ←──────────── 전체 흐름을 한 번에 테스트 ──────────→
```

| 항목 | 내용 |
|------|------|
| 테스트 대상 | UI → API → DB → 응답까지 전체 플로우 |
| 환경 | 프로덕션과 동일한(또는 유사한) 환경 |
| 예시 | "사용자가 로그인 → 상품 검색 → 장바구니 → 결제까지 완료되는가?" |
| 속도 | 느림 (전체 시스템 구동 필요) |

---

## Regression Test (회귀 테스트)

**목적**: 코드 변경 후 **기존에 잘 되던 기능이 깨지지 않았는지** 확인

```
v1.0 (정상) → 코드 변경 → v1.1
                              ↓
                    기존 테스트 다시 실행
                              ↓
                   ✅ 통과 = 회귀 없음
                   ❌ 실패 = 회귀 버그 발생!
```

| 항목 | 내용 |
|------|------|
| 테스트 대상 | 변경되지 않은 기존 기능 |
| 범위 | Unit, Integration, E2E **모두 포함 가능** |
| 시점 | 코드 변경/배포 직후 |
| 예시 | "결제 모듈 수정 후, 기존 회원가입 플로우가 여전히 정상인가?" |

> Regression Test는 테스트 유형이 아니라 **테스트 전략/시점**이다. CI 파이프라인에서 매 커밋마다 기존 테스트 스위트를 돌리는 것 자체가 회귀 테스트이다.

---

## 세 가지의 관계

범위(Scope)와 목적(Purpose)은 직교하는 두 축이다. 아래 매트릭스처럼 **조합**된다.

```
              │  Unit Test   │ Integration Test │  E2E Test
 ─────────────┼──────────────┼──────────────────┼──────────────
  Smoke       │  빌드 확인   │  API 응답 확인    │  로그인 되는지
  Regression  │  기존 함수   │  기존 연동 포인트  │  기존 사용자 플로우
  Acceptance  │     -        │  API 스펙 충족    │  요구사항 충족
```

따라서 아래 그림에서 Regression은 Unit/Integration/E2E를 **감싸는** 것이지, 나란히 놓이는 것이 아니다.

```
┌─────────────────────────────────────────────────┐
│        Regression Test (목적 — 축 ②)             │
│  "변경 후 기존 기능이 깨지지 않았는지 확인"         │
│                                                  │
│   ┌─────────┐  ┌───────────────┐  ┌──────────┐ │
│   │  Unit   │  │ Integration   │  │   E2E    │ │
│   │  Test   │  │    Test       │  │   Test   │ │
│   │ (함수)  │  │ (모듈 연동)    │  │ (전체)   │ │
│   └─────────┘  └───────────────┘  └──────────┘ │
│                                                  │
│   ← 빠름/저비용           느림/고비용 →           │
│   ← 범위 좁음 (축 ①)     범위 넓음 →             │
└─────────────────────────────────────────────────┘
```

---

## 범위 축 비교 (Integration vs E2E)

| 구분 | Integration Test | E2E Test |
|------|-----------------|----------|
| **관점** | 모듈 간 연동 | 사용자 시나리오 전체 |
| **범위** | 2~3개 컴포넌트 | 전체 시스템 (UI → API → DB) |
| **핵심 질문** | "A와 B가 잘 연결되는가?" | "사용자 플로우가 처음부터 끝까지 되는가?" |
| **CI 위치** | Build 후 | 배포 전/후 (Staging) |

## Regression Test의 위치

| 항목 | 내용 |
|------|------|
| **분류** | 테스트 레벨이 아닌 **테스트 전략/목적** |
| **적용 범위** | Unit, Integration, E2E **모든 레벨**에 적용 가능 |
| **핵심 질문** | "고친 것 때문에 딴 게 깨졌는가?" |
| **CI 위치** | 매 커밋마다 (기존 테스트 스위트 재실행) |

---

## 핵심 정리

- **Integration Test**: 모듈 간 **연결 지점**이 정상인지 확인 (범위 축)
- **E2E Test**: 사용자 관점에서 **전체 플로우**가 동작하는지 확인 (범위 축)
- **Regression Test**: 위 어떤 레벨이든, **코드 변경 후 기존 기능 보호**를 위해 재실행하는 것 (목적 축)

> 이 셋을 나란히 비교하는 것은 "사과"와 "아침식사"를 비교하는 것과 같다. 사과는 아침식사의 **일부**가 될 수 있듯, Integration/E2E Test는 Regression Test의 **수단**이 될 수 있다.
